## Рабочий регламент владельца (обязателен)

Это регламент работы, который задал владелец проекта. Он действует для тебя так же, как для Claude-сессии.

- **Ничего не писать, не менять, не удалять и не запускать без явного «да»** в ответ на твой план. Молчание, «звучит неплохо» или «ок, дальше» не считаются разрешением. Чтение, поиск (grep, cat, ls), анализ и безопасные запросы к данным делать свободно.
- **Порядок работы:** Анализ → СТОП → План → спросить «Согласовываешь план?» → СТОП и ждать ответа → Реализация → Тесты → Проверка.
- **Реализацию делаешь сам**, без субагентов. Ты и исполнитель, и проверяющий. Перед реализацией план должен быть одобрен.
- **Коммиты:** частые локальные коммиты в стиле conventional commits (`feat:`, `fix:`, `test:`, `docs:`). Вести `DEVLOG.md` с человекочитаемой записью по каждому этапу (на русском). Историю не переписывать (без rebase, amend чужих коммитов, reset с потерей работы).
- **Git с origin:** никогда не делать `push`, `pull`, `fetch` с origin без отдельного разрешения владельца на конкретное действие.
- **Пуш в закрытые репо после работы:** после изменений кода gramsrv, ботов или клиентов запускать `/usr/local/bin/sg-code-backup` (бэкап backend и bots). Для собственных проектов можно пушить в их приватный origin, но только после работы и только в приватные репо. Публичные репо `claude-gram-v2` и `opexgram-forked` и Android-исходники без git в это правило не входят: их не бэкапить и не пушить без отдельного «да».
- **Тесты pytest** на всю новую логику, включая злые граничные случаи: пустой ввод, огромный текст, юникод, попытки инъекции в атрибуты и теги, падения процессов.
- **Ответы пользователю** только через инструмент `reply` (или `reply_file` для файлов) с `format='html'`. Пользователь видит только Telegram. Ход всегда завершается вызовом `reply`, даже если ответ короткий. Обычный текст в терминале пользователь не увидит.
- **Вопросы пользователю** задавай текстом через `reply`, варианты ответа перечисляй списком прямо в сообщении. Никаких «внутренних» вопросов, которые пользователь не видит.
- **Не запускать приложение «для проверки»**, если владелец отдельно не попросил. Проверять тестами и чтением кода.
- **Не трогать чужие вещи:** не менять файлы и сервисы, которые не относятся к задаче, и не трогать боевые боты и сервисы без явного разрешения.

Почему так: владелец хочет контролировать каждое изменение и в любой момент восстановить картину по `git log` и `DEVLOG.md`, не переспрашивая.
